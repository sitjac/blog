大语言模型服务接口设计解析

Posted on 2026-05-13 In LLM
  • 当调用一个大语言模型时，调用方实际上是在选择一种与模型协作的方式，不同的 API 不仅仅是接口参数不同，它们背后是对"应用程序应该如何使用语言模型"这个问题的不同回答。
  • Chat Completions、Messages API 和 Responses API 这三种不同的 API 反映了三种不同的应用架构理念，本文深入分析它们的设计哲学、核心差异以及选型策略。

概述

目前(2026-05-13)主流的三套 API 对比：

API Endpoint 设计者 发布时间 核心隐喻
Chat Completions v1/chat/completions OpenAI 2023.03 对话补全
Messages API v1/messages Anthropic 2024 初 内容编排
Responses API v1/responses OpenAI 2025.03 任务委托

Chat Completions

设计背景

2023 年 3 月，OpenAI 随 GPT-3.5-turbo 发布了 Chat Completions API(v1/chat/completions)。

它的前身是 Text CompletionsAPI(v1/completions)，一个"给我续写这段文字"的接口，专门为单轮文本补全设计的，适用于 text-davinci-003 等较早的模型。

Chat Completions 的核心转变是：把续写的对象从"文本"变成了"对话"。

角色三元组（system / user / assistant）是这套设计最成功的地方——简单到不需要文档，人人都能直觉理解"对话"是什么。

事实标准

任何想兼容 OpenAI 生态的模型，只需实现最小 schema，就能几乎零成本接入：

`messages[]` 进，`choices[0].message.content` 出，

这是 HTTP/1.1 式的胜利：不是最优雅的，但协调成本最低，摩擦最小，网络效应使其成为事实上的行业标准。

这种结构要求开发者负责跟踪和管理整个对话历史，随着对话的进行，每次请求都要传完整的 messages[]，随着对话轮次增加，请求体会越来越大，网络传输和 Token 消耗都会显著增加。

2. 结构化输出仍然是字符串，必须手动解析

在现代软件工程中，系统之间的数据传递依赖于强类型对象，LLM 的底层本质是一个 Text Completer，它唯一的输出格式就是概率性的字符串流，早期的结构化约束输出完全靠 Prompt Engineering 去告诉模型"请输出合法的 JSON"，即使后来推出了 response_format，模型底层仍然在逐个 token 吐出字符串，OpenAI 是在模型的输出端加了一个语法拦截器，如果模型下一个 Token 敢吐出不符合 JSON 规范的字符，就强行把它的嘴捂住，逼它选择符合 Schema 的下一个字符。

这依然不是真正的类型化对象，而是通过高密度的工程护栏，硬生生把一个概率性的文本流裁剪成了看起来合规的字符串。后端依然需要做一次手动反序列化，去承受字符串解析失败的风险。

3. 工具调用的角色错位，把"工具执行结果"硬塞进"对话消息"的隐喻中

最初的 Chat Completions 设计中，大模型被隐喻为一个对话参与者。角色极其简单，只有两种：

  • user（提问的真实人类）
  • assistant（回答问题的大模型）

当引入 Function Calling 时，大模型不再只是“说话”，它开始需要干活，比如查天气、跑代码、预览文件等。但在现有的 Chat 隐喻里，没有一个"外部系统执行引擎"的位置。为了不颠覆原有的代码框架，使用这套 API 把外部程序执行返回的数据，伪装成第三个"说话者" (role: "tool")。

这就使得结构化输出是"格式合规的字符串"而非真正的类型化对象。新需求被迫挤进旧隐喻里。

Messages API

设计背景

2024 年初，Anthropic 随 Claude 3 系列发布了 Messages API(v1/messages)。它从根本上重新定义了"消息内容"，它不是字符串，而是 类型化内容块（typed content blocks） 的列表。

工具调用在这里是一等公民，不是附加字段。模型"想要调用工具"这件事被建模为内容流的一部分，而非消息上的额外属性。

核心设计

1. 显式(Explicit)优于隐式(Implicit)

OpenAI 的缓存是完全自动、隐式的，发起请求后台默默去匹配文本，匹配上了就便宜，没匹配上就贵。开发者在发请求前，无法精确预测这次到底能不能命中，只能碰运气。

Anthropic 则认为，既然代码是程序员写的，那么什么时候该省钱、什么时候该建立断点，应该由程序员在代码里明确说了算。

比如上面代码里给这一段长文本贴上了"缓存标签"，Anthropic 的服务器看到这个标签，就会强制把这一段 100k 字的系统提示词或核心文档钉在内存缓存里，从而在工程上能够做出精准的成本和性能预算。

2. 类型安全优于字符串约束

结构化输出用 tool_use 实现，返回的是已解析的 dict，不需要 json.loads。这不是字符串约束，而是协议层面的类型保证，由模型底层和输出采样器直接生成结构数据，在模型吐出 Token 的时候填充工具的参数槽。

Chat Completions 的结构化是"告诉模型输出合法 JSON 字符串"，这是字符串层面的语义； Messages API 的结构化是"模型填写函数参数对象"，这是对象类型层面的语义。

Responses API

设计背景

2025 年 3 月，OpenAI 发布了 Responses API(v1/responses)。这是三套 API 中抽象层级最高的，client 不再管理消息列表，不再执行工具，不再维护对话历史，只是下达任务，等待结果。

OpenAI 在官方博客中解释了设计动机：

"怎样让开发者以最简单、最强大的方式调用模型？"

核心设计转变在于：内置工具的执行从客户端移到了服务端。web_search、code_interpreter 等内置工具由 server 自主执行，模型自己决定何时调用、如何组合，客户端看不到中间过程。

模型在一轮请求中可能既说了话（Text）、又思考了（Reasoning）、还跑了代码（Code）、最后调用了自定义工具（Tool Call），Responses API 的返回对象变成了一个极其规范的类型化数组（Typed Items Array）。

核心设计

1. 服务端状态

previous_response_id 引用上一轮，server 自动带入历史。客户端不再传 messages[]，传的是"接着上次继续"。 便利性用控制权换来的。工具在 server 侧执行，中间过程不可见；previous_response_id 的上下文是黑盒，把透明度换成了自动化。

2. 推理控制

reasoning.effort: low/medium/high 让程序员在延迟、成本、质量之间按需权衡，这是显式控制"模型需要思考多久"的接口。

3. 内置工具

以前要在 Chat Completions 里让模型"联网搜索"或"运行代码"，需要自己写 Google 爬虫、自己在后端用 Docker 跑 Python，再伪装成 role: "tool" 喂回去。 在 Responses API 里，OpenAI 把这些能力做成了类似操作系统的系统调用程序员只需要在 tools 里像开关一样显式声明：

Responses API 的便利性用控制权换来的，工具在 server 侧执行，中间过程不可见，previous_response_id 的上下文是黑盒，高墙之内是全自动化的乐园，而高墙之外的程序员则交出了灵魂的控制权。

显式 vs 隐式

三套 API 反映了不同的设计取向：

  • Messages API 最"显式"——你标记缓存断点、你传 typed 内容块、你执行工具
  • Responses API 最"隐式"——大量决策委托给 server
  • Chat Completions 居中——客户端管历史，但缓存全自动
